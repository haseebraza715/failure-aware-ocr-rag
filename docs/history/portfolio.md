> OCR-RAG pipeline that detects its own retrieval failures and recovers — re-reading pages or answering with measured confidence, paying for visual reasoning only when needed.

## CV bullets

- **Problem:** OCR noise silently degrades RAG — retrieval still returns *a* chunk and the system still answers, confidently and wrongly, because nothing in the text path admits the evidence is unreliable. Built a pipeline where retrieval failures are first-class, detectable events.
- **Engineering decision:** replaced open-ended LLM recovery loops with a deterministic typed controller — a quality gate that emits concrete signals (word noise, layout damage, weak lexical/dense evidence), a failure diagnosis that maps signals to `word_level` / `structural` / `semantic` types, and a routing policy that pays for visual reasoning only on routed structural failures. The whole offline stack (local-hash embeddings, mock VLM, stable ranking) is deterministic and runs with no API keys or model downloads.
- **Evidence:** 155 tests green (including an end-to-end demo over a synthetic OCR-corruption corpus and a tripwire that pins committed benchmark summaries to fresh offline re-aggregation); committed 40-example OHR-Bench slice with per-example logs and a recovered-vs-direct-answer counterfactual in `logs/phase3/`; regenerable demo corpus and video in `examples/demo_corpus/` and `assets/demo/`.

## 15-second explanation

OCR noise quietly breaks RAG retrieval: the pipeline still finds a chunk and still answers — confidently and wrong. FailSafeRAG makes the failure visible and recoverable: a quality gate scores the retrieved evidence for OCR corruption and weak signals, a failure diagnosis routes to a typed recovery (OCR-text correction, retrieval retry, or selective visual fallback), and every answer carries a measured confidence. Clean questions never touch the visual model, so multimodal spend stays at zero. 155 tests, deterministic offline stack, regenerable demo.

## 45-second explanation

FailSafeRAG is a phase-1 research prototype answering one question: can an OCR-RAG pipeline detect and recover from **its own** retrieval failures? The default path is text-first: chunked OCR text is retrieved with hybrid BM25 + dense embeddings fused by reciprocal-rank fusion. A quality gate then scores the top evidence across four signals — OCR word noise, layout damage, weak lexical overlap, weak dense overlap — and either passes it to a direct answer or fails it into a diagnosis step. Diagnosis maps the failure to one of three typed recoveries: `word_level` routes to OCR-text correction (ByT5, guarded by an acceptance gate that rejects unsafe corrections), `semantic` re-queries with context-anchored evidence, and `structural` invokes a swappable VLM — the only path that spends multimodal tokens. Every answer carries a support score and mode, and the experiment runner logs per-example metrics plus a direct-answer counterfactual so recovery effect is measurable. The demo corpus in `examples/demo_corpus/` shows the whole arc: a corrupted page fails the gate on `word_noise_alert` (corruption 0.474 vs 0.053 clean), routes to word-level recovery, and answers `42%` with `support_score 9` — measurably lower than the clean page's 10 — with zero visual spend.

## Difficult staff-engineer questions

**Q1. How is the quality gate calibrated, and how do you know the thresholds are right?**

The gate (`src/faar/quality.py`) computes `quality_score = 0.40*dense + 0.35*lexical + 0.25*(1−corruption)` and emits typed reasons against four thresholds (`quality_threshold 0.52`, `weird_char_threshold 0.10`, `lexical_floor 0.10`, `dense_floor 0.20`, `structural_threshold 1`). Honest answer: the thresholds were hand-set to reproduce the failure cases found on the committed 40-example slice, not tuned by search. The evidence base does contain a measurable calibration cost: `recovery_metrics` in `logs/phase3/` shows the recovered answer changed 0 of 15 routed cases (EM/F1 effect `equal` in all 15) — i.e., on this slice the gate routes recovery where it changes nothing. That is either a conservative gate or a genuinely easy slice; distinguishing the two requires a validation sweep with a cost-weighted objective (silent-wrong-answer cost vs wasted-recovery cost) over a larger, harder sample. The tripwire test (`tests/test_evidence_tripwire.py`) at least guarantees the committed numbers cannot silently go stale.

**Q2. Why these three failure types, and what happens when the diagnosis is wrong?**

`diagnose_failure` is a strict priority chain: `structural` if layout signals reach `structural_threshold`, else `word_level` if corruption exceeds `weird_char_threshold`, else `semantic`. The taxonomy is deliberately typed and countable rather than free-form: signals → type → action is a deterministic mapping, so failures are first-class objects that can be measured, aggregated, and turned into a visual-fallback rate. The known failure mode is misdiagnosis *between* types: e.g. a page with heavy layout damage that also contains OCR noise is always routed to the VLM, and a genuinely corrupt page with clean layout is routed to word-level correction that may not help. Phase-1 mitigation is the recovery acceptance gate (`_should_accept_correction` in `src/faar/recovery.py`): a proposed correction is applied only if it preserves numeric signatures, token overlap, and length bounds — unsafe corrections are skipped and logged, so a wrong diagnosis degrades to the pre-recovery answer instead of a worse one.

**Q3. How do you measure recovery cost/benefit?**

Benefit is measured per example in `run_profile` (`src/faar/experiment_runner.py`): it computes a direct-answer counterfactual — what the extractor would answer from the pre-recovery hits alone — and records `recovery_metrics` with actual vs counterfactual EM/F1, delta, and an effect label. Cost is measured by what the routing actually executed: `action_outcome` records the action and status per example, and the visual fallback rate (fraction routed to `invoke_vlm`) is the multimodal-spend proxy. On the committed slice the benefit is zero (0/15 cases changed) and the mock VLM means real visual cost is never actually spent. The open problem is that cost/benefit has only been measured in aggregate, not conditioned on failure type or doc type — the per-example logs make that conditioning possible, but the analysis isn't done yet.

**Q4. What are the determinism guarantees, and what is not reproducible?**

Deterministic by construction: seeds are fixed (`random.seed(42)`, `np.random.seed(42)`), the default `local-hash-v1` embeddings are pure blake2b feature hashing with no RNG, retrieval uses exact inner-product FAISS (`IndexFlatIP`, no quantization) with a stable `argsort(kind="stable")` tie-break and rank-derived RRF fusion, the VLM is a mock no-op, and ByT5 is disabled in the offline profile. `tests/test_end_to_end_demo.py` asserts bit-identical graph results across repeated invokes, and the tripwire test re-runs the committed faar_full aggregation fresh and compares against the committed `artifacts/phase3/metrics_summary.json`. Not reproducible: real sentence-transformers embeddings (revision is pinned, but training/GPU numerics aren't bit-stable), real VLM answers, and ByT5 output (depends on local cache and library versions). The honest scope is: *routing decisions* are bit-reproducible; *answer quality* with neural components is only pinned by revision, not by bytes.

**Q5. What is the biggest architectural decision you would revisit at scale?**

Retrieval is per-document: `prepare_retrieval` builds the index from one example's chunks, so "retrieval failure" means failure to retrieve within the right page — there is no cross-document corpus index, and the retrieval scores on the demo corpus are therefore all-or-nothing per document. Scaling to a real corpus means moving the index to collection level, which changes what `bm25_score`/`dense_score` mean for the gate and invalidates the current threshold calibration. I would also revisit the gate's static weights: with a real benchmark (the full OHR-Bench in `data/`), the correct move is to calibrate thresholds per doc type (text vs table vs figure) and to add a calibration check — gate score vs. answer-correctness correlation — so the gate's confidence is itself measured rather than asserted. The typed recovery routing would stay: it is the difference between "agent that reasons about failure" and "pipeline that counts failure", and the latter is what makes the whole thing testable.
