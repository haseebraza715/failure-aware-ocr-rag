FailSafeRAG / FAAR

A failure-aware OCR-RAG document-QA prototype that uses text-first retrieval and invokes typed recovery only when quality diagnostics signal risk.

Evidence-backedLocal-first HTMLSource inspected

The problem it solves

Always-on multimodal OCR QA is expensive, while text-only retrieval fails on corrupt or layout-heavy documents. FAAR experiments with selective semantic, word-level, and visual recovery.

Current features

  • Phase-asset repository and OCR-aware chunking
  • Hybrid BM25+dense retrieval with deterministic local-hash offline embedder
  • Quality gate and semantic/word-level/structural diagnosis
  • Semantic query backtracking
  • Guarded ByT5 correction
  • Selective visual fallback with mock or configured backend
  • LangGraph controller and extractive answering heuristic
  • Benchmark profiles, ablations, metrics, structured logs, aggregation, and Phase 4 claim assessment

Main execution flow

  1. Load a Phase 0 example and its OCR-backed pages.
  2. Chunk OCR text and run BM25 plus dense retrieval with reciprocal-rank fusion.
  3. Score evidence quality; answer directly on pass or diagnose semantic, word-level, or structural risk.
  4. Retry retrieval, propose a guarded correction, or invoke selective visual fallback according to policy.
  5. Generate an extractive answer, compute retrieval/answer metrics, and write reproducibility metadata and route/action outcomes.
  6. Aggregate profile logs and assess cost-control, recovery-quality, VLM, and diagnosis-policy claims.

Known limitations and technical debt

  • The documented Phase 4 result does not support typed-recovery quality gain over naive RAG or selective-VLM quality gain over no-VLM.
  • The supported claim is quality-gate cost control plus diagnosis-policy alignment on the inspected offline evidence.
  • Runtime depends on phase assets under data/phase0 and artifacts/phase0.
  • pyproject dependencies are unbounded; reproducibility relies on a separate constraints file and uv.lock.
  • scripts/run_phase1_demo.sh and docs/faar_execution_plan.md contain obsolete absolute paths.
  • Thousands of committed logs and overlapping repo_architecture/repo_handbook docs make navigation heavy; generated faar.egg-info is checked in.
  • The local .venv does not contain pytest, so the documented test command did not run in that environment.
